# Arescope LAB

## When to Use

Any work on the Arescope artifacts: the web Mission Control dashboard, the Quest app (Beta 0.2 and later: scene, HUD, Copilot client, mesh/point upload), the cloud Copilot service, or a HUD design iteration. Load it before touching HUD layout, Copilot protocol or Quest build decisions; load `arescope-beta02-build-loop` as well when an APK rebuild is on the table.

Two related artifacts. Never mix their data: the web dashboard shows archived NASA terrain and synthetic walkthroughs; the Quest app is the real device capture prototype.

## Web mission control

- Source: `/root/Developer/arescope-lab` (git repo, commits are the source of truth).
- Public site: `https://arescope.mrfenek.eu.cc` — nginx on 443 proxies to a systemd unit on `127.0.0.1:18965`; TLS via certbot; DNS A record in Cloudflare.
- Cloudflare API token: `/root/.secrets/cloudflare.ini` (0600, never print).
- Terrain data checked in under `static/data/` with attribution in `docs/terrain-sources.md`:
  - `mola-gale.json` — NASA MGS MOLA MEGDR v2 crop of Gale, 65×65, ~1.85 km/px.
  - `hirise-gale.json` — NASA MRO HiRISE DTM crop, 129×129 display grid over a ~1036 m square, source step 1.0117 m, displayed step ~8.09 m (say so in the UI).
- Grid modes: `Polygonal Grid` (both diagonals) and `Minimal Grid` (axis-aligned edges only). Depth-only occluder mesh hides geometry behind the terrain.
- `static/shell.js` + `static/mission.css` hold the mission-control shell (icon rail, drawer panels, floating HUD). Test after touching it: `node --test tests/*.test.cjs` and `python3 -m pytest -q`.
- **A section moved into a drawer must lose its floating-modal styling.** Panels authored for the page often carry `position:absolute; left:50%; top:50%; transform:translate(-50%,-50%)`; appending such a section to `index.html` leaves a 680×602 modal over the map that the user reads as a broken layout. Move new sections into a pane in `shell.js` (`panes.equipment.append(live)`, `panes.settings.append(debug)`) and neutralise the styling for `.drawer-pane` descendants — `position:static`, no transform, border, shadow or background — then force one-column forms, because the drawer inherits the wide page layout.
- **Prove drawer layout numerically, not by eye.** The drawer is 350 px with a ~285 px content box; inherited grid columns and input widths push content to ~370 px, and the overflow clips the first characters of every line on the left instead of showing an obvious scrollbar. For every pane measure `pane.scrollWidth - pane.clientWidth` and count elements whose `getBoundingClientRect().right` exceeds the pane's right edge; drive both to 0 (`overflow-x:hidden`, one-column `debug-grid`, `width/max-width:100%`, `box-sizing:border-box`, `margin:0` on range inputs).
- **Verify deployed static files with the browser cache disabled.** `systemctl restart arescope-lab` plus `curl` proves what the server sends, not what the user sees; a tab holding the old `shell.js`/`mission.css` still renders the broken version. Re-check with CDP `Network.setCacheDisabled` before reloading, and tell the user to hard-refresh.
- **Check every asset the page references, not only the ones you changed.** After merging a UI branch, fetch the served HTML, extract each `/static/...` `src`/`href` and require 200 on all of them: a panel script that was never committed returns 404 while the markup still looks right, so the drawer renders and every button in it is dead. Confirm the repo carries what the HTML names with `git ls-files static/`.
- **Retire a worktree once its branch is merged, but rescue its untracked files first.** Two checkouts of the same static files drift and the deployed copy can come from either one; `git worktree remove` refuses while untracked files exist — list them with `git status --short`, copy anything real (QA screenshots, an uncommitted script) into the main tree and commit it, then remove with `--force`. Those untracked files are often exactly what the audit was missing.
- **After a feature ships, grep the UI for copy that denies it.** Lines such as "не поддерживается этим учебным прототипом", "БЕЗ LIVE-СВЯЗИ" and "Ни один режим не является live-потоком" survive from earlier versions and become false product claims once the integration lands; update the notice, header label, status pill, footer and version kicker in the same pass as the feature. Keep them consistent with what is actually verified: integration ready and awaiting the device, not "connected".
- A restarted `arescope-lab` returns 502 for a few seconds while uvicorn binds; retry the curl before diagnosing it as a deploy failure.
- **Polish the rendered screen, not the markup.** `mission.css` hides the legacy blocks (`.sidebar`, `.metrics`, `.notice`, `.panel-heading`, `.map-legend`, `.page-footer`) with `display:none!important`, so the live surface is only the topbar, the icon rail, the map stage and its empty state — audit from a screenshot and computed styles, edit the minified CSS through one appended override block, and prove every decorative layer has a non-zero `getBoundingClientRect()` before calling it more visible (`.map-grid` rendered nothing at `1280×0`). Copy stays sentence case with no tracked caps, one status per fact, no API paths in the UI, and lucide inline SVG instead of unicode glyphs. Full pass order, geometry checks and the before/after evidence workflow: `references/ui-polish-pass.md`.
- Full stale-content sweep — what to grep, endpoint cross-check in both directions, dead-code verdicts, secret patterns and the deployed-static check: `references/stale-content-audit.md`.

## Copilot and Quest integration workflow

- Before narrowing a version plan after context compression, recover the recent user decisions from session history and distinguish the complete Quest, Mission Control, mapping and assistant scope from the last feature discussed.
- Treat a question about feasibility, difficulty or whether a feature is worthwhile as a request for evaluation, not authorization to implement or rebuild. Answer with trade-offs and verification dependencies; start work only if the user requests it, and do not interpret an earlier standing build instruction as permission to begin an unrelated build.
- For this user, implement core integration and important logic in-session; delegate independent, lighter or volume-heavy UI work in isolated copies. Inspect delegated files and test outputs yourself: a textual point coordinate is not a graphical minimap, a yaw number is not a compass strip, and a disconnected settings form is not device configuration. Pass the actual endpoint schemas and event contract to delegated client work, then verify the client against server fixtures; independently invented multipart formats or SSE event shapes do not interoperate.
- Exercise streaming client boundaries with real UTF-8 split across arbitrary byte chunks, ensure deltas are wired to the HUD, and gate speech on a complete response event. Compile against the target Unity assemblies and run on Quest before claiming the client works; static source checks and a server-only smoke test do not validate Unity audio capture, playback, permissions or controller input.
- Keep live device data distinct from archived NASA terrain and simulations. Treat QuestRoomScan as a candidate for live color/geometry reconstruction, not as a verified Quest 3S build or a ready-made network stream; verify the device, permissions, performance, stream and export on hardware. Do not repeat "Quest 3S has no depth hardware": Meta's Depth API officially supports Quest 3, 3S and VR Glasses. The 3S sensor cluster is a passthrough RGB camera plus a tracking camera plus an IR illuminator, so depth is computed from the stereo RGB pair — the open risk is depth quality and scan performance, not absence of the capability.
- Copilot prototype runs ASR, structured decisions, LLM and TTS on the server; Quest records push-to-talk audio, displays streaming text and plays speech only after the complete response. Fall back to the next LLM only before emitting any answer text; if a stream breaks mid-answer, report the interruption and do not synthesize the partial response, because switching models would splice unrelated answers together.
- Jev is not OpenAI-compatible: it is the TypeSafe **System One** protocol — `POST {base}/systemone` with `{model, state, questions}`, where a question carries `type` (`choice`/`score`/`noul`), `instructions` and `criteria` (map for choice, list of levels for score). It returns typed answers with calibrated probabilities and does not stream; an OpenAI-style chat call to the same host is rejected by the provider. Keep SDM marked unavailable until its real endpoint answers with a typed decision, and never present a fabricated decision as a working SDM.
- For the SDM-to-LLM path, parse a real System One response fixture using the exact nested `answers.next_step` object and serialize the chat request as a typed `{text, context}` DTO; Unity `JsonUtility` does not serialize a raw string as a JSON string literal and cannot treat that object as an array. Validate the allowed choice and confidence before using it as advisory context; test SDM failure separately and never claim the decision was consumed without an end-to-end client test. An SDM failure must degrade to text-only answering, never block the reply.
- Keep provider credentials server-side; for a preconfigured private APK use a revocable, limited-purpose Arescope device token rather than embedding a full-access provider key. Token extraction remains possible even in a private APK, so disclose this and revoke it after testing. Do not call an unverified package a completed release merely because a version label or build was requested; distinguish server-only ASR → SDM → streaming LLM → TTS smoke tests, APK packaging checks, and the end-to-end Quest run.
- Split the Copilot service's trust roles explicitly: a panel token for the browser and a separate device token for the headset, and refuse to run when both are configured to the same value — otherwise a panel-originated acknowledgement becomes indistinguishable from a device acknowledgement. Put the device credential in a `Resources/` config inside the APK for internal test builds so it can be swapped without touching code, and state plainly that such a token is extractable from the package.
- Serve the cloud Copilot service on its own loopback port with a dedicated systemd unit and a dedicated nginx location prefix on the Mission Control host; keep the existing lab site on its own location untouched and re-check the lab root still returns 200 after the nginx change. Put router, SDM and provider keys in a 0600 environment file, not in the repo or the APK.
- Copilot service coordinates: source of truth `/root/Developer/arescope-beta02-core` (`app.py`, `copilot_core.py`), deployed copy `/opt/arescope-copilot`, unit `arescope-copilot.service` on `127.0.0.1:18975`, env `/etc/arescope-copilot.env` (0600). Verify drift with `sha256sum` on both copies before assuming a prompt or TTS change is live, copy the changed module, restart, then hit the status route; a prompt-only change never needs an APK rebuild.
- Quest HUD: put connection statuses upper left, transient events lower left, minimap upper right, streamed assistant text lower right, compass upper center and voice state lower left beneath transient events, with a car-navigation-style arrow for the minimap position marker; the user explicitly swapped left and right while keeping the compass centered. Support hard and smooth following, constrain the full HUD during head motion, and verify against both eyes on the headset. Preserve minimap distance and use a clipped, moving compass strip with a fixed marker. Label the strip with real cardinal letters (N, NE, E, SE, S, SW, W, NW every 45°) plus a bearing ruler of ticks every 5° — taller on the 15° marks, a bold tall tick under every cardinal, letters on their own row above the ticks. Every tick, cardinal and minor alike, uses the same ink and alpha (`Rule` #513026 at 0.9) and differs only in size; the user rejected a copper accent on the cardinal marks, so keep that emphasis in geometry, never in a second colour, and accept that the ruler reads softer than a coloured one. All ticks are positioned with `Mathf.DeltaAngle(yaw, bearing) / 180 * stripWidth`, which spreads the strip over about 180° of visible bearing. Keep the `LOCAL` prefix on the heading readout: the headset has no magnetometer, so N is the session's start orientation, not geographic north. The settled styling after review: leave the top row (status, compass, map) where it is and pull the side cards deep toward the centre — the user asked twice for more inset, and the final value is 112 units from the canvas edges (about 9% of the 1280-wide canvas) for status, event, voice, map and assistant alike, which leaves 50–70 units of clearance to the centred compass without overlap; a "few units" nudge will be rejected. Lift the bottom row clear of the lower edge of vision because it was uncomfortable to glance at, keep card fills translucent (settled at roughly 75% transparency, fill alpha 0.25 in Linear colour space, so passthrough stays visible), and draw the minimap as a round instrument with the car-navigation chevron.
- Render the actual Unity HUD to PNG for each design iteration using the editor-only `RenderArescopeHudPreview.Run` and a graphics-capable display; inspect clipping, overlap and text legibility. Send the PNG as a full-quality document in the main chat and obtain the user's review before building the redesigned APK. `/root/Developer/arescope-beta02-questroom/HUD-PREVIEW.md` documents the isolated temporary scene and RenderTexture workflow. A mono, flat-background image cannot verify Quest stereo, passthrough, lens legibility or head movement.
- Seed the review render with a representative fixture — 3–4 status rows, an active voice state, a few minimap contacts, a sentence of Copilot text — because the untouched empty state renders as dashes (`SYSTEM STATUS —`, `VOICE —`) and the user cannot judge density or legibility from it; keep one env switch for the bare state and label fixture copy as a preview, never as live telemetry.
- Size cards from the rendered line count and re-render after any content change: `VerticalWrapMode.Truncate` drops trailing rows, and generated row rects shorter than one line-height render nothing at all (Manrope 16 needs ≈23 units per line plus padding). Fix height, not type size. Full rules: `references/unity-hud-components.md`. Verify on a cropped zoom that every intended row is present and that `CONTACTS n` matches the visible dots — a point under the centre chevron still counts and reads as a bug.
- Verify the render numerically before sending it: read the PNG with PIL/numpy, sample the background colour from a corner, threshold the per-pixel difference and print each card's bounding box and row bands. A vision model reads geometry unreliably — it calls a clipped row present, misjudges alignment and miscounts dots — so use bounding boxes for geometry and vision only for legibility and taste. Recipe and interpretation: `references/hud-render-verification.md`.
- **Audit a render for defects before delivering it, and state what is still wrong.** The user treats a delivered render as a claim that the scene is correct, so a frame containing sky where a wall should be, a black mass, or furniture floating above the floor is a defect report owed to them, not a screenshot. Ask the vision model explicitly to enumerate defects by location ("what is wrong in this frame, with position"), keep asking after each fix pass, and separate fixed items from ones you chose not to fix and why.
- A circular minimap needs a real stencil (`Mask` over a circle-fan graphic), not `RectMask2D`, and the user removed its grid outright — leave the face empty apart from header, contacts and chevron. Geometry, safe-area insets and marker centring: `references/unity-hud-components.md`.
- Reach for Meta XR Simulator before another headset trip: it is Meta's own OpenXR runtime that runs the Unity app on a PC with Quest 2/3/3S profiles, keyboard, mouse and controller input, synthetic rooms that supply passthrough, scene data, anchors and (Windows only) environment depth, and VRS session record/replay. It does not run the APK, so packaging, launcher and lens checks still need the device. It ships for Windows and macOS only, and environment depth is Windows-only; a laptop-class discrete GPU (GTX 1650 tier) is enough because it renders a window rather than two 90 Hz eye buffers, while a 2013-era Kepler mobile GPU is not. Setup, limits, and what is still unverified: `references/no-headset-quest-testing.md`.
- **Before every headset session, hand the user three things: the APK as a file, a runbook and a controller map.** The deliverable is the actual `.apk` attached in the chat (path under `MEDIA:`), not only a URL — state size, package id, `versionCode` and SHA-256 beside it and keep the shared-host link as a mirror. Then a short markdown file in the project: install command, the numbered scenario (launch → scan → move → mode switch → PTT → finalize) with the expected HUD text at each step, the post-run check in Mission Control, and what to collect when a step fails (`adb logcat -d`, `adb shell screencap -p`). State per step what counts as a failure and what you will do about it, and list the known-risky unknowns separately so they are not mistaken for new regressions. Include the controller bindings as a table: the left controller's `primaryButton` is **X** and `secondaryButton` is **Y** in Unity, so X starts and finalizes the scan, Y toggles passthrough ⇄ scan view, and holding the right grip is push-to-talk — there are no other bindings, so say that triggers, sticks and right-hand buttons are unused rather than leaving the user to guess. Pre-flight the artifact before writing it: the producer token baked into the APK must still match the server's, and both the APK and the SIM PC archive must answer a ranged `GET` (a `HEAD` returning 403 from the shared host is not an outage).
- **Do not churn the artifact you are about to validate on hardware.** When a device session is imminent, answer a "can we build?" question by naming what is already published — URL, SHA-256, versionCode — before proposing another build, and disclose the remaining known defects instead of a bare "no blockers". If a change is still wanted, ship it as a new `bundleVersion`/`bundleVersionCode`, keep the previously published APK live as a rollback, and prove the scripts compile (a `RenderArescopeHudPreview.Run` pass compiles every script) before paying for IL2CPP. If the new build fails twice, stop and keep the known-good version.
- **The Quest project renders through URP.** `Shader.Find("Standard")` returns a shader that draws magenta in this project (`ProjectSettings/GraphicsSettings.asset` points at `UniversalRenderPipeline`); always build materials from `Universal Render Pipeline/Lit` and set `_BaseMap` / `_BumpMap` / `_Smoothness` rather than `Material.color` alone. Check `mat.shader == null || mat.shader.name.Contains("Hidden")` and fall back explicitly, so a missing shader surfaces as a warning instead of a magenta scene.
- **A procedurally built mesh renders pure black in URP/Lit until it has UVs and tangents.** With `_NORMALMAP` enabled and no `mesh.uv`/tangents the shader gets a degenerate basis and the surface lights to zero — it still occludes the sky, so the frame reads as a black silhouette, not as a missing mesh. After building vertices, set `mesh.uv` from the X/Z extent and call `mesh.RecalculateNormals()` then `mesh.RecalculateTangents()`.
- **Any generated mesh above 65 535 vertices needs 32-bit indices.** `Mesh.indexFormat` defaults to 16-bit, so a 257×257 terrain (66 049 vertices) wraps its triangle indices and renders as a black slab across the sky plus torn holes at the horizon and long diagonal seams — symptom-for-symptom it imitates a broken material, a bad camera or fog. Set `mesh.indexFormat = UnityEngine.Rendering.IndexFormat.UInt32` before assigning `vertices` and `triangles`.
- **Imported CC0 furniture needs orientation and scale verified numerically, not by eye.** Poly Haven FBX exports are Z-up and mixed — some import upright, others lying on a side — and `ModelImporter.bakeAxisConversion` does not reliably fix it. Rotate the instance (`Quaternion.Euler(0, yaw, 0) * Quaternion.Euler(rotX, 0, 0)`), and note the sign matters: `rotX=-90` on the dining chair produced an upside-down chair where `+90` stood it upright. Fit by the smallest per-axis ratio against a target box (never by height alone, which blows the footprint up), then log scale/size/center/min and compare those numbers across models before rendering. When a model's measured bounds disagree with expectations, fetch the asset's glTF (`https://api.polyhaven.com/files/<asset>` → `gltf.1k.gltf.url`) and read `POSITION` accessor `min`/`max` — that is the reliable truth for real dimensions, and a large mismatch means the FBX carries extra geometry that should be dropped or replaced.
- **Camera poses over generated terrain must be relative to the surface, and eye height needs interpolation.** A camera placed below the local heightfield renders the terrain as a black silhouette; sample terrain height instead of guessing an absolute altitude (`SIM_RENDER_GROUND=1` in `BuildSimScenes.RenderViews`). At eye height the 8 m lattice matters: the nearest vertex sits below the interpolated surface and drops the camera inside the mesh, so bilinear-sample the four surrounding vertices and add 1.8 m. For a review frame that puts the real HUD over the Mars scene (`BuildSimScenes.RenderMarsHud`), be prepared for URP to leave the facing slope unlit — swap the terrain to `Universal Render Pipeline/Unlit` with the same `_BaseMap`, render, restore, and tell the user the surface is albedo rather than a lighting study. Set `cam.aspect = 1600f / 900f` and rebuild the projection matrix before rendering into a RenderTexture — a stale aspect from the previous screen size squeezes the world-space HUD, tightens its line spacing and lets the compass overlap the status card, and the user reads that as a design regression rather than a render bug. Full test-scene setup — room contents, model and texture sources, HiRISE crop, render env vars: `references/sim-test-scenes.md`.
- Never draw a card border with `Outline`/`Shadow`: they re-emit the graphic mesh behind the fill and an opaque effect colour silently kills translucency. Stroke the border inside the same `MaskableGraphic` mesh via `borderColor`/`borderWidth` and let the mesh fill alpha be the only opacity knob — recipe in `references/unity-hud-components.md`.
- Emit repeated hairlines — compass ticks, any surviving grid — from one mesh, not one `Image` per line: a 1-unit `Image` is subpixel at HUD scale, so lines land on different pixel phases and the drift is obvious inside a masked card. Details in `references/unity-hud-components.md`.
- Once fills reach roughly 75% transparency the fill can no longer carry text contrast against bright passthrough: give glyphs their own dark edge (`Shadow`, black at about 0.7 alpha, `effectDistance` (1,-1)) instead of quietly raising panel alpha again, which is the change the user asked to avoid.
- Put an icon on every status row and take icons from a ready-made set (Tabler via iconify, MIT) rather than drawing geometry — the user asked for exactly that. Five slots only; more statuses need a layout change. Glyph list, rasterising, keyword mapping and the `Resources.Load<Texture2D>` + `Sprite.Create` loading rule: `references/unity-hud-components.md`.
- **When a status line outgrows its card, widen the card — never abbreviate the label.** The user explicitly chose more panel width over shorter copy; the status card went 240→300 units to fit `UPLINK 200 2s` and still renders unclipped. Bind transport rows to the sender's real result instead of a placeholder: `LiveFrameSender` exposes `LastStatusCode`, `LastSuccessAt`, `LastStored` and `LastThrottled` as static properties, and `ScanProgressHud` renders `UPLINK WAITING | 200 Ns | TIMEOUT | 401 AUTH | 200 cap`. That makes a dead uplink visible inside the headset, without removing it to check the browser, and the `cap` suffix separates "server accepted" from "server persisted". Refresh the status block on every tick, not only while `scanner.IsScanning`: a time-derived row (`UPLINK 200 2s`) otherwise freezes at its last value the moment the scan stops and reads as if the signal were current. Keep the cost down by joining the composed rows into a signature and calling `SetStatuses` only when it changed.
- Show instrument state without making the user read a word: give the voice card a five-bar input meter fed by a public `SetVoiceLevel(float)` so a dead microphone is obvious before speaking, paint the minimap contacts counter copper only when contacts exist and muted for `NO CONTACTS`, and set section headers (`SYSTEM STATUS`, `FIELD EVENT`) in the muted tone so the values read first. Feed the meter a synthetic level in the review render and say it is synthetic.
- Keep the tested box project and the local repo in step, and treat a file sitting in `Assets/` as unwired until its `.meta` exists and the scene references that GUID: a copied-in script with no `.meta` was never imported, no scene object can carry it, and the feature it implements simply does not run — check `.meta` and grep the scene for the GUID before believing a component is attached. Mirror `Assets`, `Packages`, `ProjectSettings` and every `.meta` back into the repo, copy anything local that differs into a timestamped backup instead of overwriting silently, and never delete local-only files. `scripts/sync_from_instabox.py` performs the pull from a `sha256sum` manifest and prints what was added or updated.
- **The Unity project is a git repo; keep data caches out of `Assets/`.** `Assets/` is imported by the editor, so a multi-tens-of-MB raw PDS `.bin` staged there is both a build liability and repository bloat — keep such caches in a scratch directory outside the project (e.g. `~/.hermes/cache/scratch/hirise-cache/`) and gitignore them. Generated scenes are reproducible from `BuildSimScenes`, but commit them anyway: they exist only on the sandbox until pulled, and the user treats a single-copy asset as a loss risk. `.gitignore` must cover `Library/ Temp/ Build/ *.apk` and the IDE outputs; `.git` for this project lands around 24 MB with textures and models included.
- Local sources and the box are separate filesystems: push the edited `ArescopeHudController.cs` and `RenderArescopeHudPreview.cs` before rendering with `PUT https://api.instabox.sh/v1/machines/<machine>/files?path=<abs path>&mode=0644` (body = file bytes, header `X-API-Key` from `~/.hermes/instabox.key`), then pull the PNG with `GET …/files/content?path=<abs path>`. Compare the returned `sha256` with the local file so a stale copy never gets rendered.
- Match the live Arescope LAB design by reading its current CSS before redesign: its mission-control palette uses warm carbon and copper, not generic cyan, with Manrope for human-readable copy and DM Mono for instrument labels. Embed full-quality font files with their licences and check glyph coverage; DM Mono lacks Russian glyphs, so use Manrope for Cyrillic. Use `Resources.GetBuiltinResource<Font>("LegacyRuntime.ttf")` as the Unity 6000.2 fallback, not `Arial.ttf`, which throws at runtime. Render the actual HUD after changing fonts.
- For a proposed live top-down minimap, distinguish an altitude slice from wall classification: a height band can suppress floor and ceiling, but furniture at that height remains. Cull points outside the map bounds instead of clamping them to its edge, and clip the viewport. Gate implementation on actual Quest depth/scan validation, then measure FPS and readback cost on-device. Three sources get confused here, so name the one a change binds to: a sampler over `RoomScanSession.RefinedMeshRenderer.sharedMesh` produces nothing during the scan and points only after refinement (an empty circle mid-scan is expected, not a bug); the live vertex buffer sits behind internal types (`GPUSurfaceNets`, `PointCloudExporter` are reachable only inside the `Genesis.RoomScan` assembly — 48-byte stride, position at offset 0, active count in the counters buffer), so a live feed needs a documented package patch that is re-applied with the other patches after every re-resolve — and that patch must ship a sibling `.meta`: a `.cs` dropped into `Library/PackageCache` without one is skipped with `Asset … has no meta file, but it's in an immutable folder`, and every caller then fails to compile with `CS0103: The name … does not exist`. A GUID that is not exactly 32 hex characters is worse: the editor exits before `-executeMethod` runs, the log stops right after `SDL leaked 2 allocations`, and there is no `error CS` to chase — hand-written GUIDs like `aresc0pe...` look plausible and break the import of the scope.
- **The LAB viewport has three layers, and the scan mesh travels as a second, separate payload.** `static/layers.js` owns a switch (Архив / Live / Скан) that draws its own three.js canvas above the archive canvas instead of touching `app.js`: hide the archive canvas and `#map-empty` with `style.display` when a non-archive layer is active (`#map-empty` carries `display:flex`, so the `hidden` attribute does nothing), hide the archive reload button in the same mode, and set the header label from the active layer so the topbar cannot contradict the viewport. The mesh upload is `POST /api/live/mesh?session={id}` (producer token) with the ARSM binary — `ARSM`, uint32 version 1, vertexCount, indexCount, then float32 positions, uint8 RGBA colours, uint32 indices, little-endian, cap 32 MB — stored per session and served back through `GET /api/live/sessions/{id}/mesh` (viewer token), with `hasMesh`/`meshBytes` surfacing in the session list. On the headset the data comes from `PackagePatches/ArescopeMeshExport.cs` inside the RoomScan assembly (counters buffer for the vertex count, `DrawIndirectArgs[0]` for the index count, 48-byte vertex stride, position at 0, packed colour at 36, async readback of both buffers), called once from `MeshUploader` on `RoomReady`; `LiveFrameSender.LastSessionId` supplies the session. Readbacks arrive as `NativeArray<byte>`, which `BitConverter` rejects — copy to a managed array first. Render a room mesh with `side: BackSide` and place the camera inside the bounding sphere: from outside a closed shell reads as a plain box, and the point of the layer is standing in the room.
- **Textured scans need ARSM v2, and the atlas already exists on the headset.** `RoomScanner.LastRefinedResult` (internal, reachable from a package patch) carries `Positions`, `UVs`, `Indices` and `AtlasPixels` (RGBA32) once on-device texture refinement has run — no re-unwrap and no re-bake is needed, just read the finished result. v2 appends, after the v1 indices, `float32 UV[2×V]`, then `uint32 atlasWidth`, `uint32 atlasHeight`, `uint32 pngLength` and the PNG bytes; the server locates the atlas block at `16 + V×16 + I×4 + V×8` and validates `pngLength` against the remaining body, while v1 stays valid for scans that never refined. Preferences: try v2 first and fall back to vertex colours, never the reverse; write white vertex colours in v2 so a missing atlas reads flat rather than muddy; downscale the atlas to ≤2048 and `EncodeToPNG()` before upload. Two costs to disclose: encoding a 2048² RGBA atlas runs on the main thread and can hitch a frame on XR2, and the resulting payload can approach the 32 MB cap. In the browser, `createImageBitmap(blob)` into a `THREE.Texture` with `flipY = false` and `colorSpace = SRGBColorSpace`, on a `MeshStandardMaterial({map})`; label the layer with which variant arrived (`текстура 2048×2048` vs `вершинные цвета`) so a missing bake is visible instead of silent.
- **Name what QuestRoomScan already gives you before planning more capture work.** The SDK ships four distinct quality tiers: raw TSDF geometry, vertex-coloured mesh, on-device texture refinement (`Reading mesh from GPU` → `UV unwrapping` → `Baking (GPU)`, which turns a washed-out mesh into a recognisable textured room while leaving warped furniture and projection seams), and Gaussian Splatting training that requires an external GPU server (`GS Training`, thousands of iterations, the demo points at a LAN host). Only the first two are reachable through the plain vertex/index buffers; textures need UVs plus a baked atlas carried alongside the mesh, and splats need a GPU host you do not have on the VPS. Say which tier a change binds to, and prefer extending the mesh format with UVs and an atlas over trying to make vertex colours look like a photograph.
- **A scan that starts and then reports `frames=0, depthAvail=False, sub=null` is missing the Meta OpenXR plugin, not a scanner bug.** `com.unity.xr.meta-openxr` is a project-level dependency of QuestRoomScan that is absent from the package's own `package.json`: without it `AROcclusionManager` has no `XRDepthSubsystem` provider, the TSDF volume still allocates 32 MB, and the failure surfaces far from its cause — finalize throws `NullReferenceException` in `AROcclusionManager.DestroyTextures` and texture refinement reports `Mesh readback returned no vertices`. Install `2.4.1` (matches OpenXR 1.15.1; it pulls ARF 6.4 and `com.unity.xr.compositionlayers`), enable the AR Foundation Meta features for Android together with the `MetaOpenXR-OpenXRLifeCycle` feature, confirm the XR loader still auto-starts, and only then bisect: add plane/mesh/anchor one at a time after a clean boot. An abort at `xrCreateInstance` with zero `[RoomScan]` lines is the loader/plugin/lifecycle layer failing, not a verdict on the feature set — see the three gates at the top of `references/quest-depth-openxr.md`. Feature ids, the script that flips `m_enabled`, the build-validation trap and the device log signature: `references/quest-depth-openxr.md`. Two traps that cost several build cycles each: **installing the package is not enough to get its native code** — `libUnityARFoundationMeta.so` can be omitted from the APK even with the plugin marked Android/ARM64, so copy it into `Assets/Plugins/Android/arm64-v8a/` and assert it with `unzip -l <apk> | grep libUnityARFoundationMeta.so` before bisecting anything, because a `DllNotFoundException` for that library looks exactly like a feature problem; and **the runtime's extension support is queried too early and cached**, so `instanceProcAddr is null` + `This OpenXR runtime doesn't support XR_META_environment_depth` while OVRPlugin already listed the extension means the subsystem was never created, not that depth is unsupported. Full chain, log signatures and the `ARSession` restart workaround: `devops/unity-quest-xr-diagnostics`. The root cause behind the false extension verdict is a **disabled `MetaOpenXR-OpenXRLifeCycle` feature**: it is what binds the native function table, so with it off every capability probe sees `instanceProcAddr is null`, caches "unsupported", and the occlusion subsystem is never created — restarting `ARSession` at runtime cannot clear that cache, only a rebuild with the feature enabled. Enable it together with the AR features, and check that `m_AutomaticLoading`/`m_AutomaticRunning` in `Assets/XR/XRGeneralSettingsPerBuildTarget.asset` are still `1`: a package upgrade resets them to `0`, the loader stays listed but never runs, and the app renders flat with "No active XR loader" in the log.
- **Log the device run so one grep reads it, and so a native crash leaves evidence.** `Debug.Log` carries a stack by default, which turns a 40-second run into 25 000 lines; call `Application.SetStackTraceLogType(Log, None)` and `(Warning, None)` at `BeforeSceneLoad`, keep stacks only for errors, and put every message under one `[ARS] area | k=v` tag. Mirror each line synchronously to `Application.persistentDataPath/arescope-debug.log` — a `SIGABRT` kills the process between frames and logcat can lose the tail, while the file survives and is pulled with `adb pull /sdcard/Android/data/<pkg>/files/arescope-debug.log`. A heartbeat once a second during the scan plus an 8-second no-progress warning with an XR snapshot turns "it doesn't work" into a named step. For collection: `adb logcat -c` first, launch via `am start -n <pkg>/com.unity3d.player.UnityPlayerGameActivity`, take screenshots through a device file and `adb pull` (`adb exec-out screencap -p > file` corrupts the PNG under PowerShell), and convert a PowerShell-redirected log with `iconv -f UTF-16LE -t UTF-8` before grepping. Log format, collection script, decision table and pitfalls: `references/device-log-pipeline.md`; ready-to-copy logger: `templates/CompactUnityLogger.cs`.
- Live ingest into LAB exists now: `POST /api/live/frame` (Bearer = producer token, body `{room, yawDeg, points:[[x,y,z]…]}`, max 4096 points), `GET /api/live/latest` and WebSocket `/api/live/stream?token=…` (Bearer/query = viewer token). Frames are stamped `source: "live-quest"`, kept per-room with a 30 s TTL, and the panel (`static/live-panel.js`) renders them on a canvas — never mixed with archived NASA data. Two deployment traps: the public site serves `master`, so a panel that exists only on a side worktree/branch is not deployed until it is merged and `arescope-lab` restarted; and the arescope nginx location needs `proxy_set_header Upgrade $http_upgrade` + `Connection "upgrade"` with `proxy_http_version 1.1` (now added as a dedicated `location /api/live/stream`) — without it the handshake returns 404 over HTTP/2 and 403/404 over HTTP/1.1, and a WebSocket-only viewer shows nothing in production. Test the handshake with `curl --http1.1 -H 'Upgrade: websocket' -H 'Connection: Upgrade' -H 'Sec-WebSocket-Version: 13' -H 'Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ=='` (expect `101 Switching Protocols`; plain curl over HTTP/2 cannot upgrade). The stream is a real push: `_subscribers` holds one `asyncio.Queue` per viewer, `_broadcast` fans out on POST, a late viewer gets a snapshot of `LIVE_FRAMES` on connect, and a 20 s keepalive ping stops proxies from reaping the socket. The panel still falls back to polling `/api/live/latest` every 2 s after a failed handshake, so verify end to end with a producer `POST /api/live/frame` while a `websockets` client is connected to the public origin, not just the static file returning 200. Tokens come from env (`ARESCOPE_LIVE_PRODUCER_TOKEN` / `ARESCOPE_LIVE_VIEWER_TOKEN`), stored in `/etc/arescope-lab.env` (0600) and `/root/.secrets/arescope_live_tokens`. Every accepted frame is also appended to a SQLite history (`ARESCOPE_LIVE_DB`, default `/var/lib/arescope-lab/live.sqlite3`; points are gzipped): sessions split on a 60 s gap, pruned by `ARESCOPE_RETENTION_DAYS` (7) and `ARESCOPE_MAX_DB_BYTES` (200 MB). `GET /api/live/sessions` + `GET /api/live/sessions/{id}` are viewer-scoped and return only the LAST stored frame of a session (`source: archived-quest`); `DELETE` needs the producer token. This is a decimated stream (≤4096 points, every 3 s), not a reconstruction — a full-fidelity archive needs a mesh export from the device. Serving a large number of rows to the narrow drawer means one column and `overflow-x:hidden` per pane; verify with `scrollWidth - clientWidth` rather than by eye. The Quest side is `Assets/Arescope/LiveFrameSender.cs` (sends every 3 s, ≤384 points, token in `Resources/arescope-live-token.txt` — extractable, disclose it). Scan progress on HUD is `Assets/Arescope/ScanProgressHud.cs`, subscribed to `RoomScanSession.ProgressUpdated`/`RoomReady` (`ScanProgress.OverallProgress`, `ScanPhase` enum).
- **Before a headset session, replay the device cadence against the public origin.** The GPU readback is the only part that needs hardware; token, DNS, TLS, nginx, ingest, history and viewer readback can all be proven first by posting the same payload the APK sends (384 points, yaw, room `default`, every 3 s, Bearer producer token) for about a minute, then asserting one session, the expected frame count, `maxPoints` 384 and a readable `archived-quest` frame. It turns a device failure into a yes/no about the device. Ready to run: `scripts/simulate_device.py`.
- **Interval guards look broken when tested one request at a time over TLS.** A fresh HTTPS connection costs more than a 0.25 s throttle window, so three sequential POSTs all come back `stored:true` and the guard seems missing; fire the burst on one keep-alive socket (`http.client.HTTPSConnection` reused across requests) and the second and third correctly return `stored:false, throttled:true`. Same trap for any rate limiter: latency dominates a small window unless the connection is reused or the window is widened deliberately for the test.
- **The Mission Control drawer is a different layout on a phone, and that is where the viewer token gets typed.** At 390 px the rail becomes a bottom bar and the drawer a ~366 px sheet: confirm `scrollHeight > clientHeight` with `overflow-y:auto` (action buttons legitimately sit below the fold), keep the close target at 44×44, add bottom padding so the last field is not flush with the edge, and give the 43-character viewer token a paste-from-clipboard button (`navigator.clipboard.readText()` needs HTTPS plus a real user gesture; show a manual-entry message when it is denied) instead of making the user type it.
- The live minimap is now wired: `ArescopeLiveCloud.SampleAsync(Vector3[] destination, int maxPoints)` sits inside the RoomScan assembly and returns decimated raw scan-space vertices (counters buffer for the live count, async readback of the vertex buffer, unsafe pointer reads so no per-sample allocation), and `Assets/Arescope/LiveScanMinimap.cs` throttles it every 1.5 s, keeps a ±1.4 m height band around the head plus a 10 m radius cull, and calls `SetMapPoints(points, range, scanCloud: true)`. Render a scan cloud with smaller markers than contacts — 9-unit dots overlap into a solid wall bar at map scale, 3.2 units reads as discrete points — raise the cap to 192 and label it `POINTS n` rather than `CONTACTS n`. Scene wiring goes through `WireArescopeScene.Run` so the component lands on `ArescopeCopilot` with a saved scene. The preview accepts `ARESCOPE_PREVIEW_MAP=walls` for a synthetic room outline that demonstrates the look, and that fixture is not evidence the device feed works. Patterns, code shape and what is still unverified on hardware: `references/live-scan-feed.md`.
- Expose HUD controls in Mission Control; distinguish settings persisted on the server from settings actually applied on the device. Bind device acknowledgement to the current settings version and a recent heartbeat, and authenticate the device separately from the panel before trusting that acknowledgement; an old or panel-originated acknowledgement is not proof that the headset applied settings.
- For a QuestRoomScan scene, inspect the preset's side effects before running it: create and validate the XR rig, passthrough, depth/occlusion, scanner, shader references and required Android permissions as separate gates. A scene that merely contains component types is not a functional scanner; Quest 3S depth, native texture refinement, exported model and live network transport each require their own device-level verification.

### Build environment lessons (InstaBox)

- Unity `6000.2.9f1` + Android Build Support installed via Unity Hub into `/data/home/Unity/Hub/Editor/6000.2.9f1`.
- Meta XR packages must be **83.0.4** (81.0.0 does not compile) and need Linux patches inside `Library/PackageCache/com.meta.xr.sdk.core@*/`. The patches now live in the repo as `scripts/patch_meta_sdk_linux.py` (run after every PackageCache reset) — apply them from there, not by hand-editing the cache.
- Headless (`-batchmode -nographics`) import works only with an active Unity license; a signed-out Hub yields `Error building player because build target was unsupported` plus entitlement 404s. Register a `unityhub://` scheme handler before the browser sign-in or the OAuth handoff dies.
- `BuildPipeline.IsBuildTargetSupported(Android)` must be probed in the same run — a stale `ProjectSettings` can report unsupported. Unity 6.2 stores Android platform settings in a build profile, so also write them via `EditorUserBuildSettings.SetPlatformSettings`.
- **Remove `com.unity.burst` from the project** before building: with the Meta XR sample stack present, Burst's `bcl.exe` workers sit at 0% CPU and stall `IL2CPP_CodeGen` indefinitely on an 8 GiB builder.
- The InstaBox disk (20 GiB) is the binding constraint: editor + Android module ≈ 15 GiB. Do not delete `Data/Resources/PackageManager/Editor` — without it no packages resolve. Move `Editor/Data/PlaybackEngines/AndroidPlayer` to the root volume behind a symlink, and run the project from the volume with more free space.
- A fresh minimal Unity project will not compile Meta XR packages until the built-in engine modules are declared in `Packages/manifest.json` (`com.unity.modules.animation`, `androidjni`, `assetbundle`, `physics2d`, and the rest the errors name). Add only the modules the log asks for; a missing one surfaces as `CS1069 … forwarded to assembly`.
- A pinned third-party package may target a newer editor API than the installed one. Patch only the copy inside the project, keep the original next to it as a backup, and prefer a scripted patch over hand edits — the package cache is wiped on re-resolve.
- Unity's build can report `Succeeded` while the packaging step logged an error, so read the `BuildReport` summary counts, not the exit code, and then verify the artifact itself: unzip integrity, `aapt dump badging` for package id/SDK/ABI, and the presence of `launchable-activity`. A missing launcher activity means the APK cannot start even though the build passed.
- A custom `Assets/Plugins/Android/AndroidManifest.xml` replaces Unity's, so it must itself declare the launcher activity, its intent filters (including the Oculus VR category), the theme, and every permission the app needs — otherwise the packaged manifest has no way to launch.
- Meta OpenXR rejects non-linear color space: set `PlayerSettings.colorSpace = Linear` before building.
- The IL2CPP step on an 8 GiB builder is killed when stale compiler daemons from earlier runs still hold memory — check for leftover `dotnet`/`VBCSCompiler` and Unity processes and stop only those before rebuilding. Free disk by deleting build-generated caches (`Library/Bee`, `Library/Artifacts`, Gradle cache), never the project sources, and copy the produced APK out first.
- **Give the builder swap and ~12 GiB before a release build, and check what the package is carrying.** The box has no swap by default: the OOM killer takes the `Unity` process itself (`dmesg | grep 'Killed process'`, anon-rss around 2.5–3 GB) because total memory runs out first — `sudo` is available, so `sudo fallocate -l 4G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile` on the **root** volume, not `/data`, or you trade a memory failure for a disk one. 9 GiB free is not enough: a run that dies with `LLVM ERROR: IO failure on output stream: No space left on device` inside `:unityLibrary:stripReleaseDebugSymbols` is disk exhaustion at final packaging, not a toolchain bug — reach ~12 GiB (also drop the editor's unused `PlaybackEngines/WindowsStandaloneSupport`, ~0.7 GiB and reinstallable via the Unity CLI, and `/data/home/.cache`, ~2 GiB) and retry. The Android build must also carry **only** the headset scene: once the simulator-scene generator runs, `EditorBuildSettings.scenes` also lists `SimRoom`/`SimMars`, and a 10 MB generated terrain in the APK is what pushed earlier attempts over the limit — filter in the build entry point (`.Where(s => s.enabled && s.path.Contains("QuestRoomScan"))`) and throw when it matches nothing, then bump `bundleVersion`/`bundleVersionCode` and confirm both with `aapt2 dump badging`. Three triage rules from that loop: a run that stops about half a minute in with `BeeDriver connection terminated` / `Tundra build interrupted` and no `error CS` is the editor being killed, not a compile failure — confirm with `dmesg | grep 'Killed process'`, free memory, retry — and it leaves the previous APK sitting in `Build/`, so check that artifact's timestamp and `versionCode` instead of trusting the path; clearing only the Gradle `caches` tree can strand a transform, so a later `java.lang.IllegalArgumentException: .../transformed/output/jdkImage` inside `:unityLibrary:compileReleaseJavaWithJavac` means delete the whole `/data/home/.gradle` and let Gradle re-download; and a `HEAD` request to the shared host answers 403, which is not an outage — probe artifacts with a ranged `GET`.
- Native helper libraries the package expects (for example a UV-unwrapper `.so` for ARM64) can be cross-compiled from the package's own C++ sources with the NDK clang in the Android module, but the result must be verified inside the APK (`lib/arm64-v8a/…`) and on the device.
- E2B cannot host this build: `min_free_disk_mb` is capped at 25600 and a base sandbox has ~22 GiB / 2 vCPU. Daytona (50 GiB) exists but large downloads reset the connection.
- **Building a Windows PC player on the Linux box (for Meta XR Simulator):** the `windows-mono` Hub module is not installed by default — install it with the Unity CLI that is already on the box: `/data/home/.local/bin/unity install-modules -e 6000.2.9f1 -m windows-mono --accept-eula -y` (runs ~5 min, needs ~700 MB free; module lands in `Editor/Data/PlaybackEngines/WindowsStandaloneSupport`). Build entry point `Assets/Editor/BuildSimPc.cs` → `-executeMethod BuildSimPc.Build` → `Build/SimPC/ArescopeBeta03.exe`, Mono2x backend, `StandaloneWindows64`. Do NOT call `PlayerSettings.SetArchitecture(..., Architecture.x64)` — that API does not exist in 6000.2 (`CS0103`); x64 is the default for that target. Tar the whole `Build/SimPC/` folder for transfer; run the exe from the unpacked folder on the Windows laptop with the simulator running. See `references/no-headset-quest-testing.md`.
- **Always launch batchmode Unity with `-quit`.** A build or scene-generation run started without it finishes its `-executeMethod` work but leaves the editor process alive holding `Temp/UnityLockfile`; every later `-batchmode -quit` invocation then exits within a second emitting only `SDL leaked 2 allocations`, with no output from the method, and a stale `.log` that ends right after `Successfully changed project path`. That is a held lock, not a compile error: check `ps aux | grep "[U]nity"`, kill the stale PIDs, remove `Temp/UnityLockfile`, then re-run.
- **Disk pressure on the 20 GiB box:** orphan Unity/Licensing/ILPP processes from killed builds hold several GiB — before rebuilding, `ps aux | grep Unity`, kill only those PIDs, then remove `Library/Bee|Artifacts|BurstCache|ShaderCache|ScriptAssemblies` and `/data/home/.gradle/caches`. Verify with `df -h /data` (target: ≥9 GiB free before a build). At 100 % the build dies in the profiler writer — a `StreamWriter.Dispose` / `Bee.Core.TinyProfiler2.WriteChromeTrace` exception plus `No space left on device` — after compilation already succeeded, so do not read it as a code failure; the failed run also leaves the previous APK in `Build/`, so compare its timestamp and `versionCode` before shipping.
- **Issue cache cleanup as its own plain command.** Bundling `rm -rf Library/... /data/home/.gradle/caches` into one compound line with `df`/`grep` makes the whole invocation wait on a destructive-command approval; when that approval is not answered, none of the line runs and the next build starts against a full disk. Run the read-only checks first, then the deletion as a separate call, then `df -h /data` to confirm free space.
- **`aapt`/`aapt2` are not on the InstaBox PATH.** Verify a packaged APK with `/opt/unity-android/SDK/build-tools/36.0.0/aapt2 dump badging <apk>` and grep for `package:`, `targetSdkVersion`, `launchable-activity` and `native-code`.
- **systemd env propagation is not automatic:** adding `EnvironmentFile=` pointing at a file whose keys don't match the expected env names silently leaves them unset. After any env change, verify in the live process: `tr '\0' '\n' < /proc/$(systemd show <unit> --property=MainPID --value)/environ | grep <PREFIX>`. Prefer a dedicated env file with the exact variable names (e.g. `/etc/arescope-lab.env`, 0600) over reusing a secrets file with different key names.
- Details, URLs and sizing numbers live in the separate `unity-android-headless-builds` skill, which carries its own `references/unity-linux-environment.md` and `scripts/patch_meta_sdk_linux.py` inside that skill's directory.
